# linux-omarchy-dtbs

The Snapdragon laptops get no device tree from their firmware. Their UKI carries one for each laptop (`DeviceTreeAuto=`), and systemd-stub picks it by the laptop's hardware IDs. This package installs those trees under `/boot/dtbs/linux-omarchy/qcom`, and under `/usr/lib/systemd/boot/hwids/aa64/linux-omarchy` the hardware IDs systemd's own list doesn't have yet. `linux-omarchy` shipped both itself until `7.3-46` and now depends on this package, so the two always come together. This package in turn depends on the kernel whose headers it was built from, or a newer one, so new trees never install next to an older kernel.

## How it builds

`linux-omarchy-headers` ships the sources of every tree the kernel build makes, the files they include, the dt-bindings headers and the kernel's own `dtc` ([`linux-omarchy-aarch64`](../linux-omarchy-aarch64/README.md#snapdragon-laptops)). `prepare()` copies those sources and applies this recipe's `*.patch` files to the copy. `build()` compiles every `qcom/*.dts` in it with the headers' `dtc`, the way Kbuild does. There is no kernel build, so a new laptop's tree ships in a minute.

Every tree gets the symbols an overlay needs (`-@`). Kbuild adds them only to the trees that have an EL2 variant, 50 of 72, and those 50 are the same bytes as the kernel package's at `7.3-42`. The other 22 differ only by the symbols, which add about 1 MB to the 14 MB of trees, and an overlay can then go on any of them.

`.omarchy/package.json` rebuilds this package (`rebuild_on`) once a new `linux-omarchy-aarch64` is on edge, so the trees follow the kernel's tree patches within a sync. The package's description names the kernel the trees were built from (`pacman -Qi linux-omarchy-dtbs`), which shows trees that trail their kernel.

From `7.3-43` the package depends on `systemd-stub-omarchy`. A UKI holds each tree as a PE section of its own, and since `7.3-42` there are more trees than Arch Linux ARM's systemd stub has header room for (about 119), so ukify stops with "Not enough header space". `systemd-stub-omarchy` is the same systemd release's stub with room for 1024, which Omarchy's boot image builds use once it is installed; as a dependency it arrives in the same transaction as the trees, before any boot image is built with them.

## Adding a laptop

- A tree, or a fix to one the kernel ships: a patch in kernel format (`git format-patch` against the kernel's tree), added to `source` and `b2sums`. It can only touch files under `arch/arm64/boot/dts/` or `include/dt-bindings/`, so a posted patch loses its `Makefile` and binding hunks first. Every `qcom/*.dts` is built, so a new tree needs no `Makefile` line. Patches apply in the order of `source`.
- Hardware IDs systemd doesn't list: the laptop's `.json` file, added to `source` and `b2sums`. The notes on the hardware ID files are in the kernel's README, with each laptop. A patch's notes are below.

A patch stays here until the kernel moves to a new version. Then `pkgver` follows it, `pkgrel` starts again at 1, and the patches the new kernel has are dropped. If the kernel's recipe takes a patch from here before that, `prepare()` finds it in the kernel's sources, skips it and raises a warning on the CI run, and the patch can go. A patch that neither applies nor is in the sources stops the build.

## Patches

`0001` adds the Surface Laptop 7 15" (`x1e80100-microsoft-romulus15`) touchpad, a HID-over-SPI device on `spi19`, using the Surface Pro 11's spi-hid and QSPI patches in the kernel. On its own the pad stays in a mouse mode: pointer, tap and press to click. iptsd adds two-finger scroll, pinch and two-finger tap, but press to click stops registering, because iptsd doesn't decode the pad's haptic report yet. `0063` covers the 13.8". By Jason Bruce Jones.

`0063` adds the same touchpad to the Surface Laptop 7 13.8" (`x1e80100-microsoft-romulus13`): the node `0001` gives the 15", on the same `spi19` wiring (interrupt GPIO 3, supply GPIO 65, reset GPIO 120), which the ELLX kernel shares between both sizes. It enumerates as `045E:0C77` with no SPI bus errors. The pad then stays silent until the EC has its posture events enabled (SSAM TC 0x01, CID 0x0b, payload `26 01 26 00 00`, as Windows sends at boot); with that done the pointer moves and clicks. Tested on the 13.8". By Caleb E.

`0064` to `0066` give the 13.8" the touchscreen, video codec and front camera that `0029` to `0031` give the 15", with the same nodes. The 13.8"'s touchscreen is on `spi10` like the 15"'s: the shared romulus ACPI tables describe it as `\_SB.GTCH` on QUP1 SE2 for both sizes, and only boards reporting TBID 2 or 3 take an I2C branch (`\_SB.ITCH`, 0x34 on `i2c8`). It enumerates as `045E:0C6E` and iptsd runs it. Iris loads the same `qcvss8380.mbn` from `microsoft-surface-laptop-7-firmware` and decodes H.264 in hardware. The OV02C10 binds at `12-0036` and streams 1080p through libcamera's simple pipeline, dark like the 15"'s without tuning. Tested on the 13.8". By Caleb E.

`0067` powers the Surface Laptop 7 13.8"'s digital microphones (`x1e80100-microsoft-romulus13`). The shared card routed `VA DMIC0` and `VA DMIC1` to the WCD938x's `MIC BIAS3` and to a `VA MIC BIAS3` the VA macro doesn't have, so nothing turned on the macro's `vdd-micb` supply (`vreg_l1b`) and the microphones ran unpowered: one channel was full-scale noise, the other silent. The 13.8"'s tree now gives both `vdd-micb` and a 2.4 MHz clock, as on the Surface Pro 11. On the 13.8" a speaker tone shows in both channels of PipeWire's internal microphone through alsa-ucm-conf's Surface Laptop 7 profile, and DMIC2 and DMIC3 carry nothing, so its two microphones are DMIC0 and DMIC1. The 15"'s microphones work with the shared routing, so `romulus.dtsi` keeps it and the 15"'s tree doesn't change. By Caleb E.

`0002` adds the Lenovo IdeaCentre Mini 01Q8X10 with the Snapdragon X X1-26-100 (`purwa-lenovo-ideacentre-mini-01q8x10`), on the board file the kernel's `2821` splits out of the X1P-64 model's tree. systemd's own hardware IDs already pick it. The compatible follows the binding in `2820`, so it ends in `qcom,x1p42100` where Jens Glathe's latest tree has `lenovo,thinkpad-t14s`, `qcom,x1e80100`. It loads its firmware from `qcom/x1p42100/LENOVO/91B6`, which `lenovo-ideacentre-mini-x-firmware` installs. By Jens Glathe.

`0003` and `0004` fix the LCD Surface Pro 11's tree (`x1p64100-microsoft-denali`, Snapdragon X Plus X1P-64-100). Its LG LP129WT3 panel takes its brightness from a PWM signal and ignores eDP AUX brightness, so `0003` drives a `pwm-backlight` from PMK8550 PWM channel 0 out of GPIO5, as on the Surface Laptop 7. The part has 10 cores, and `0004` deletes the fused-off CPU7 and CPU11, which PSCI refuses to start. Both work on the kernel's existing drivers. The kernel's `2157` gives the remaining cores in those clusters cpufreq, and `2160` adds the panel's timings. By Iván Ruiz.

`0005` gives the HP OmniBook X 14 (`x1-hp-omnibook-x14.dtsi`, both variants) its internal microphones. The two mics are on VA DMIC0 and DMIC1 and are powered by the WCD938x's MIC BIAS1, but the tree routes them to MIC BIAS3, as the CRD's does, so capture powers the wrong bias and the mics record silence. The patch routes DMIC0 and DMIC1 to MIC BIAS1 and VA MIC BIAS1, as the ThinkPad T14s's and the Zenbook A14's trees do. Found and tested by TheArtForm on an OmniBook X 14-fe0, where speech records on both channels through the laptop's UCM profile with no workaround (basecamp/omarchy#17396). LukeMech found the same bias on this model. The X1P-42-100 variant shares the file and hasn't been tested.

`0006` gives the Acer Aspire 16 AI (`x1p42100-acer-aspire-16-ai`) its sound card, wired as the ThinkBook 16's. It has two WSA8845 speaker amplifiers on the WSA bus, the WCD9385 headset codec, the two lid microphones on VA DMIC0 and DMIC1, and DisplayPort playback on both USB-C ports and HDMI. The microphones run at 2.4 MHz, because 4.8 MHz gives loud static. The card loads its topology from `acer-aspire-16-ai-audio`, and its UCM profile is in `alsa-ucm-conf`. Worked out and tested by GenericCPU on an A16-11M (omacom/omarchy#17555). The Aspire 14 AI shares the dtsi but not this card, since its speaker wiring isn't known.

`0007` lets the Surface Laptop 7's Wi-Fi (`x1e80100-microsoft-romulus.dtsi`, both sizes) ignore its rfkill pin. The WCN7850's hardware rfkill input reads as "radio off", so Wi-Fi comes up hard-blocked and never connects. The laptop has no Wi-Fi switch, and Windows ignores the pin through an ACPI setting a device tree boot doesn't see. ath12k skips the pin when the node has `disable-rfkill`, as the Surface Pro 11's and Surface Laptop 8's trees have it. Tested on the 15"; the 13.8" shares the node and hasn't been tested. By Jason Bruce Jones.

`0068` enables the Surface Laptop 7's third PCIe controller only on the 15" (`x1e80100-microsoft-romulus15`). It leads to the 15"'s microSD reader, an RTS5261, but the controller, its PHY, the root port's reset and wake GPIOs and its pin state were in the shared `x1e80100-microsoft-romulus.dtsi`, so on the 13.8", which has no card reader, the host probed, found no device and kept its PHY, clocks and power domain on. They move to the 15"'s tree unchanged: its tree compiles to the same nodes and properties as before. Measured on the 13.8": `1bd0000.pcie` logged "Device not found" at every boot and `lspci` showed only the empty root port `0003:00:00.0`.

`0069` lets the Surface Laptop 7 (`x1e80100-microsoft-romulus.dtsi`, both sizes) read its charge limit back at boot. `qcom_battmgr` sets the limit through the battery firmware (`charge_control_start_threshold` and `charge_control_end_threshold`), and the firmware keeps it in PMK8550 SDAM `0x7e00`. Without nvmem cells on the `pmic-glink` node the driver can't read it, so sysfs shows 0/0 after every boot whatever the firmware enforces, and the driver has nothing to send again when the battery service restarts. The node gets the three cells `hamoa-pmics.dtsi` already defines, as the X1 CRD's and the Acer SFA14-11's trees use them. On the 13.8" the firmware writes that layout: enable, end and delta read 1/80/5 at `0x73`/`0x75`/`0x76` after setting an 80 % end, and 1/100/5 after a 95 % start. Booted on the 13.8" with the change, the driver reads the limit back (95/100 where it read 0/0), and a limit set before a restart reads the same after it. The 15" hasn't been checked. The driver doesn't fail safe: if the layout were wrong, with a non-zero enable byte and a delta at least the end, its probe fails and the battery and charger supplies disappear.

`0008` to `0011` give the Dell XPS 13 9345 (`x1e80100-dell-xps13-9345`) its sound card. `0008` adds its four WSA8845 amplifiers, two woofers and two tweeters on the WSA and WSA2 buses, and the speaker and microphone links, from Sibi Sankar's patch as Aleksandrs Vinarskis carries it. `0009` powers the two digital microphones from the LPASS microphone supply, by Aleksandrs Vinarskis. `0010` routes the right woofer from SPK1, which matches its SoundWire ports. `0011` switches the card to `dell,xps13-9345-sndcard`, so the kernel's `2451` plays four-channel streams to the right pair first, as the XPS 13 is wired. Without `2451` the card doesn't bind, so these need `linux-omarchy` 7.3-61. Its UCM profile is alsa-ucm-conf's own. Adapted and tested by 42lizard (Oliver Gassner), with all four channels on the right side after a clean boot (omacom/omarchy-pkgs#2293).

`0071` gives every Hamoa and Purwa tree fixed GIC LPI tables for hibernation. `0072` restricts the `cluster_cl5` cluster idle state in `glymur.dtsi` to `s2idle` by raising its `min-residency-us` from `9000` to `1000000000` (1000 s) instead of dropping it from `cluster0_pd`, `cluster1_pd` and `cluster2_pd`. On the ASUS Zenbook A16 (UX3607OA), entering `cluster_cl5` during runtime cpuidle causes random hard freezes and spontaneous restarts with no kernel log (omacom/omarchy#19916); keeping `min-residency-us` at 1000 s keeps runtime `Usage=0, Rejected=0` while leaving `cluster_cl5` attached to the clusters so `s2idle` can enter `cluster_cl5` + `domain_ss3` (`0x0200c354`) cleanly instead of spinning on `PSCI_RET_DENIED` (`-1`).

`0073` drops `com_aux` (`GCC_USB3_TERT_PHY_COM_AUX_CLK`) from `usb_2_qmpphy` in `glymur-asus-zenbook-a16-ux3607oa.dts`, split out from omacom/omarchy-pkgs#3579 (by Roman Stingler). On the ASUS Zenbook A16, `usb_2_qmpphy` is a DisplayPort-only PHY driving the onboard HDMI bridge (`parade,ps185hdm`) with no DWC3 behind it; enabling `com_aux` stalls at halt (`gcc_usb3_tert_phy_com_aux_clk status stuck at 'off'`), causing `qmp_combo_com_init()` to fail with `-EBUSY` and leaving `HDMI-A-1` uninitialised. Because `qmp_combo_clk_init()` fetches the bulk clocks with `devm_clk_bulk_get_optional()`, overriding `clocks`/`clock-names` to keep `aux`, `ref` and `usb3_pipe` lets the PHY initialise cleanly (verified at boot with HDMI-A-1 connected and EDID/modes read in #3579; HDMI across s2idle not yet tested). Stopgap to drop on the 7.4 rebase once Wesley Cheng's upstream qmp-combo USB-clock split lands.

`0074` adds the front camera of the Anduril BlueChip (`glymur-anduril-bluechip`), an OmniVision OV08X40 RGB sensor on CSIPHY4 in 4-lane mode behind `cci1_i2c1`, powered by a PM8010 camera PMIC on `i2c5`. From the board's Windows camera configuration (`CAMF_RES_QRD.bin`, `CAMP_RES_QRD.bin`, `SCFG_FRONT_QRD.bin`, `qsh_camera_ov08x_2.json`), the sensor sits at 7-bit I2C address `0x10` (8-bit `0x20`), PM8010 reset is GPIO 106, sensor reset is GPIO 239, MCLK4 (GPIO 100) runs at 19.2 MHz (4 mA), and the sensor rails are PM8010 LDO7 (2.8 V AVDD), LDO4 (1.8 V DOVDD) and LDO2 (1.1 V DVDD, 1.104 V on the PM8010 NLDO 8 mV step grid). Tested on the Anduril BlueChip on `linux-omarchy 7.3.6-4`: PM8010 (`2-0008`), `ov08x40` (`9-0010`), `csiphy4` and `qcom-camss` bind cleanly with zero kernel errors and stream 1920x1080@30fps through `libcamera` and `v4l2-relayd`. Needs `linux-omarchy>=7.3.6-4` for Glymur CAMSS, standalone CSI2 PHY and PM8010-over-I2C support.

`0075` drops `wakeup-event-action = <EV_ACT_DEASSERTED>` from `gpio-keys/switch-lid` (TLMM GPIO 92, active low) in `glymur-asus-zenbook-a16-ux3607oa.dts`. Armed for the rising edge only, the lid hall-sensor IRQ fires and immediately wakes the laptop (~0.6 s after suspend) whenever the SoC exits CX collapse with the lid already open, matching the Surface Laptop 8 fix in `2384`. Without `wakeup-event-action`, opening a closed lid still wakes the laptop while open-lid suspend stays asleep in `cxsd`/`aosd`/`ddr`.

`0076` drops `wakeup-event-action` (inherited as `<EV_ACT_DEASSERTED>` from `glymur-crd.dtsi`) from `gpio-keys/switch-lid` in `glymur-anduril-bluechip.dts`, preventing the same spurious open-lid wake on CX collapse exit while preserving lid-open wake from closed-lid sleep.

`0077` drops `wakeup-event-action` (inherited as `<EV_ACT_DEASSERTED>` from `x1-asus-zenbook-a14.dtsi`) from `gpio-keys/switch-lid` in `x1p42100-asus-zenbook-14-ux3480qa.dts`, preventing open-lid `deep` suspend from waking on CX collapse exit while preserving lid-open wake from closed-lid sleep.
